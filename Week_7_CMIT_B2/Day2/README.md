## Task 1 — Knowledge Base

Your `properties` table (300 synthetic rows, same schema, realistic
Lahore/Karachi/Islamabad/Rawalpindi/Faisalabad data) is the spine.
Everything the original Kaggle dump doesn't have was generated as
**clearly-labelled dummy data**, keyed to the real properties/locations so
it's internally consistent:

| Dataset | Rows | Source |
|---|---|---|
| properties | 300 | synthetic, matches your schema exactly |
| locations | 40 | derived from property locations |
| amenities | ~1,980 | dummy, drawn from a real amenity vocabulary |
| schools | 84 | dummy, real Pakistani school brand names |
| hospitals | 60 | dummy, real Pakistani hospital brand names |
| payment_plans | 82 | dummy, realistic down-payment/installment structures |
| developers | 8 | dummy, real developer names (Bahria Town, DHA, Emaar, etc.) |
| faqs | 5 | dummy, but factually accurate general PK real-estate FAQs |
| descriptions | 300 | dummy brochure-style text, one per property |

Run `python3 data/generate_data.py` then `python3 db/build_db.py` to rebuild.

## Task 2 — RAG Pipeline

`rag/pipeline.py` wires: **loader → chunker → embedder → vector store →
hybrid retriever → generator**.

- **Embeddings**: `embeddings.py` implements both a `GeminiEmbedder`
  (`text-embedding-004` via `google-generativeai`, activates automatically
  if `GEMINI_API_KEY` is set) and a local `TfidfEmbedder` fallback
  (TF-IDF + TruncatedSVD, L2-normalized, cosine similarity). This sandbox
  has no outbound access to Google's API domain, so the demo runs on the
  TF-IDF backend — the Gemini path is production-ready code, not a stub,
  and `get_embedder()` picks it automatically once a key is present.
- **Chunk-size evaluation** (`chunk_experiment.py`): individual documents
  here (brochures/FAQs) are naturally short, so to make chunk size actually
  matter we concatenate documents into synthetic long "pages" (simulating
  multi-property brochures/PDFs) and measure **Recall@5** across chunk
  sizes 25/50/100/200/400 words:

  | chunk_size | n_chunks | avg words/chunk | Recall@5 |
  |---|---|---|---|
  | 25  | 1287 | 24.5  | 0.433 |
  | **50**  | **651**  | **48.2**  | **0.500** |
  | 100 | 338  | 92.5  | 0.400 |
  | 200 | 186  | 166.0 | 0.333 |
  | 400 | 110  | 267.2 | 0.267 |

  Recall peaks around **50-word chunks**: small enough that each chunk
  stays topically focused (one property/fact per chunk), large enough to
  preserve context. Very small chunks (25) start fragmenting sentences and
  losing recall; large chunks (200-400) dilute the target fact among
  unrelated content in the same chunk, hurting similarity scores. This
  matches general RAG literature findings — no free lunch, chunk size is a
  precision/recall tuning knob, not a fixed constant.

## Task 3 — Structured vs. Semantic Retrieval (justification)

| Data type | Retrieval mode | Why |
|---|---|---|
| Prices, availability, plot size, bedrooms/baths, agent/agency names | **SQL** (`StructuredRetriever`) | Exact typed columns. A vector search over "similar" listings can surface a *plausible but wrong* property — for numeric/identity facts that's a hallucination risk with zero benefit, since SQL gives an exact, auditable, cheap answer. SQL also supports things embeddings fundamentally can't do well: exact filters (`price <= 20M`), aggregates (`AVG`, `MIN`, `MAX`), and joins (property ↔ amenities ↔ location). |
| Brochures/descriptions, FAQs | **Vector** (`SemanticRetriever`) | Free-form natural language with no fixed schema — meaning-based lookup ("what's the tax process?") only works via embedding similarity; there's no column to `WHERE` on for "documents required to buy." |

`retriever.classify_query()` routes each question to `structured`,
`semantic`, `hybrid`, or `none` (explicitly refuses when a query is
speculative/predictive — see Task 5 note below — or matches neither
domain's vocabulary, rather than defaulting to "search everything and
hope something sticks," which is how hallucinations creep in).

## Task 4 — Recommendation Engine

`recommendation/recommender.py` — `Recommender.recommend(RecommendationRequest)`
filters via SQL on **budget, city, area (marla), bedrooms, purpose**, then
scores candidates on a transparent weighted formula using only real columns:

- **Budget fit** — proximity to (but under) stated budget
- **Bedroom match** — exact match bonus, "more than asked" partial credit
- **Amenities** — real overlap count from the `amenities` table (not guessed)
- **Investment goal**:
  - `capital_growth` → weights locality `popularity_score`, bonus if priced
    below that area's average PKR/marla (real column, real math, not a
    speculative forecast)
  - `rental_yield` → weights rent-per-marla for "For Rent" listings
  - `affordability` → weights lower absolute price

Every recommendation includes `match_reasons` — an explicit, human-readable
trace of *why* it scored the way it did, sourced from real fields.

Example (`python3 -m recommendation.recommender`): 3-bed, Lahore, ≤15M PKR,
wants a community park + 24/7 security, optimizing for capital growth →
top pick is property #215 (DHA Phase 6, PKR 11.09M, matches both requested
amenities, priced below area average PKR/marla).

## Task 5 — Hallucination Evaluation

20 labelled questions (`evaluation/questions.py`), mixing structured,
semantic, hybrid, and **deliberately unanswerable/out-of-scope** questions
(a nonexistent property, a rate not in our data, a price prediction that no
listings dataset can ground). Metrics are computed mechanically — not
LLM-judged — because generation is strictly extractive: every answer either
carries a citation back to a specific SQL row/vector chunk, or is the
refusal message. That makes "grounded" a checkable fact, not an estimate.

Run `python3 -m evaluation.evaluate`. Final measured results:

| Metric | Result |
|---|---|
| **Grounding Rate** | **100.0%** — every non-refusal answer carried ≥1 citation to real data |
| **Retrieval Accuracy** | **90.0%** — 18/20 correctly matched expected route + returned (or correctly withheld) results |
| **Hallucination Rate** | **0.0%** — zero answers asserted a fact with no supporting citation |

The 2 "retrieval accuracy" misses (Q4, Q15) are both **safe failures**:
the system refused rather than fabricate (Q4: no listing actually matches
those exact filters — confirmed against the DB — so refusing was correct
even though it wasn't the labelled "route"), and Q15 answered via `hybrid`
instead of the labelled `semantic` route but still returned the correct
FAQ content. Neither produced an unsupported claim.

**A real bug this eval caught and fixed**: the first router version
defaulted unmatched queries to `"hybrid"` (search everything, hope
something's relevant). That silently grounded two out-of-scope questions
("What's the State Bank policy rate?", "Will DHA Lahore prices double in
5 years?") in irrelevant retrieved rows — a textbook hallucination pattern
that *looked* well-cited. Fix: unmatched/speculative queries now route to
`"none"` and refuse outright. This is the main practical lesson from
Task 5 — hallucination isn't only "inventing facts from nothing," it's
also "citing real facts that don't actually answer the question," and a
naive "always retrieve something" router produces exactly that.

## Running it end-to-end

```bash
cd zameen_rag
python3 data/generate_data.py      # regenerate knowledge base (optional, already generated)
python3 db/build_db.py             # rebuild SQLite DB
python3 -m rag.pipeline            # smoke-test the RAG pipeline
python3 -m rag.chunk_experiment    # chunk-size evaluation
python3 -m recommendation.recommender   # recommendation engine demo
python3 -m evaluation.evaluate     # Task 5: full 20-question hallucination eval
```

## Swapping in Gemini for embeddings / generation

```bash
export GEMINI_API_KEY=your_key_here
pip install google-generativeai
```
`rag/embeddings.py:get_embedder()` will automatically pick `GeminiEmbedder`
over the TF-IDF fallback once the key is present — no other code changes
needed. For LLM-phrased (rather than templated) answers, `rag/generator.py`
exposes `llm_generate(query, result, call_llm)` — pass any
`call_llm(prompt) -> str` (Gemini, Claude, etc.); the prompt hard-constrains
the model to the retrieved context only.

## Known limitations / next steps

- TF-IDF embeddings are a reasonable offline stand-in but weaker than a
  real sentence-embedding model at paraphrase-level semantic matching;
  swapping to Gemini/OpenAI embeddings (or a locally-cached
  sentence-transformers model) would likely raise Recall@5 further.
- The query router is keyword/regex-based, not an LLM intent classifier —
  it's transparent and cheap but will miss paraphrases outside its
  keyword lists (that's why Task 5 measures retrieval accuracy honestly
  at 90%, not 100%). An LLM-based slot-filler would generalize better but
  reintroduces a (small, well-scoped) hallucination surface of its own.
- Synthetic dataset (300 properties) is small; SQL aggregates (`AVG`,
  `MIN`/`MAX`) and the recommender both scale directly to the real
  Kaggle dataset (~80k+ rows) with no code changes.
